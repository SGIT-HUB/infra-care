# Linux 服务日志轮转

适用于 Linux 上服务文件日志的轮转配置与排查。本文依据官方文档整理，具体发行版调度方式、服务重开机制和实际效果待任务中验证。其他平台不套用 Linux 命令。

## 先确定日志由谁管理

确认服务实际写入文件、journald、syslog 还是容器标准输出，以及已有的轮转策略和日志用途。优先沿用对应日志系统的保留机制，避免多个轮转器同时处理同一文件。不因日志持续增长就直接新增 logrotate 配置。

需要 logrotate 时，核对目标绝对路径、匹配范围、文件属主与权限、现有配置、状态文件和实际调度入口。调度可能来自 cron 或 systemd timer；不能假设总由 root 的每日 cron 执行。

## 轮转方式和服务差异

- 优先确认服务是否支持重开日志。Nginx / OpenResty 的 `USR1` 用于重开日志，`HUP` 用于重载配置，不能混为一谈；信号目标需核对当前实例的 master PID、权限和容器边界。
- Redis 等服务须依据对应版本和实际日志实现判断轮转方式。不要套用 Nginx 的信号，也不要把重复执行 `CONFIG SET logfile` 当作已验证的通用重开机制。服务不需要重开时，不增加 postrotate 命令。
- 使用重命名方式时，核对新日志创建权限和后续写入目标。`delaycompress` 可推迟压缩，但不能代替服务正确切换日志。
- `copytruncate` 的复制与截断之间存在丢日志窗口；仅在无法采用合适重开机制且任务接受该取舍时考虑，不将其作为默认无损方案。
- 按实际日志用途、增长量和可用空间确定保留与压缩策略，不把开发环境天数推广为生产或审计要求。

## 调度环境与凭据

定时执行不保证继承交互 shell 的 PATH 或环境变量。postrotate 使用已核对的可执行路径、身份和必要环境，保留失败信息，不以 `|| true` 无条件掩盖关键操作失败。

优先采用无需数据库凭据的日志管理方式。确需鉴权时，从本机受限的 `local/private.json` 中按现有部署机制取用，核对执行身份的访问权限；不要将密码写入公共模板、命令行参数或另一份长期凭据文件。若目标服务需要受限运行配置，记录其位置和同步关系，不在公开文档保存实际值。

## 验证与收尾

先对实际选定的配置使用 logrotate 的 `--debug` 模式检查匹配范围和计划动作；该模式不修改日志或状态文件，也不能证明 postrotate 已成功执行。

强制轮转会实际修改日志、保留集合和状态，不属于只读检查。仅在任务授权范围内安排一次受控验证，确认新日志持续写入、权限正确、旧日志停止增长、压缩与保留符合预期，并核对调度执行结果。任一步失败就停止后续切换，按本次方案恢复，不扩大清理范围。

本机档案记录实际配置、日志位置、调度方式、验证结果和剩余工作。临时整理副本遵循仓库 backups/ 规则；业务日志和业务备份不作为临时副本删除。
