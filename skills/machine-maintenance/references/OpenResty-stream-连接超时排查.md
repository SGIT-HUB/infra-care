# OpenResty stream 连接超时排查

适用于经 OpenResty / Nginx stream 代理访问 Redis、PostgreSQL 等服务时的连接中断。以 TCP 空闲连接为主要排查场景；UDP 会话需另核对其响应与超时语义。本文依据官方文档整理，实际环境的路径、配置和处理效果待任务中验证。

## 先建立判断依据

1. 确认实际运行的程序、版本、启动参数、配置入口及 include 文件；容器内外路径分别核对，不假设固定安装目录。查看完整配置可能包含敏感信息，不复制进公共记录。
2. 记录断连间隔、连接是否空闲、客户端错误，以及同条件下直连和经过代理的差异。直连稳定仅帮助定位链路，不足以单独证明代理超时是根因。
3. 核对目标 stream server 的显式配置、上级继承值和当前生效状态，区分磁盘文件与运行中的配置。

Nginx 官方文档中 `proxy_timeout` 默认值为 `10m`，表示客户端或上游连接两次连续读写之间的超时。它不按 Redis、PostgreSQL 分别设置默认值；特定环境观察到的 60 秒或 180 秒不能推广为协议默认值。OpenResty 的实际行为仍需结合所用版本和有效配置核对。

若空闲时长与有效超时值一致，可将其列为候选原因，同时排查客户端连接池、后端空闲策略、负载均衡、防火墙和 NAT 的超时。仅凭时间吻合不直接下根因结论；持续有流量仍断连时，扩大到对应链路和应用错误排查。

## 变更与验证

仅在定位和授权范围内调整相关连接的配置：

- 根据应用的空闲时长、心跳和连接资源占用选择 `proxy_timeout`，不统一套用一小时或无限时长。
- `proxy_connect_timeout` 控制建立上游连接的等待时间，不能替代会话读写超时；HTTP 的超时指令也不能直接用于 stream。
- 使用运行实例对应的二进制、配置参数和权限先做语法检查，再通过实际服务管理方式重载。检查失败就停止重载，不扩大变更。
- 重载后新建连接，分别验证业务读写、预期的空闲时长及重新使用连接的结果，并观察日志。平滑重载保留的旧连接不能单独证明新配置已生效。
- 不符合预期时恢复本次改动并重新验证。将实际配置位置、修改值、验证条件和剩余疑点记入本机档案；公共文档只保留通用判断。
